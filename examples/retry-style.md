# 接口重试：专业表述与易懂解释

**问题：** 接口重试里，退避、抖动、重试额度和幂等分别防什么问题？

下面用同一段意思展示“专业表述 → 易懂解释”的变化。**这是表达方式示意，不是两份模型实测回复。**

**未使用 Skill 时可能看到的专业式表述（示意）：**

> 某 SDK 对可重试的失败采用 exponential backoff 与 jitter，并通过基于 token bucket 的 retry quota 约束重试预算。持续失败扩大退避窗口并消耗额度，成功请求可恢复额度；jitter 下的单次等待值不一定逐次增长。对支持 client token 的操作，在接口规定的幂等范围内保持相同 token 和参数，避免重试产生重复副作用，但不保证操作成功。

**应用 Skill 指导后的易懂解释（示意）：**

> 调用接口的程序遇到允许重试的失败时，这些机制管的是不同问题：什么时候再试、还能试多少次，以及重复请求会不会把同一件事做两遍。
>
> - **指数退避（exponential backoff）**：请求失败后先等一等再试。连续失败时，逐步扩大可选择的等待时间，减少立刻反复请求带来的压力。
> - **抖动（jitter）**：让多个程序在等待时间内随机选一个时刻再试，错开重试，避免又同时涌向服务。因此，下一次实际等待不一定比上次长。
> - **重试额度（retry quota、token bucket）**：把还能重试的额度当作一笔预算。持续失败会消耗预算，成功请求可以补回；预算耗尽就停止重试，避免故障被更多请求放大。
> - **幂等与 client token**：超时不一定代表服务端没执行。client token 相当于这次操作的请求编号；重试时沿用原编号和相同参数，并满足接口规定的处理范围，就能避免同一操作被重复执行。处理范围可能按地区等条件划分，具体以接口约定为准。这只适用于支持该机制的接口，也不保证请求一定成功。

变化是把“退避、抖动、令牌桶、幂等”等术语，连接到等待、错开请求、重试预算和重复操作这些具体动作，同时保留适用条件。
