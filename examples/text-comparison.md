### 未显式加载 Skill：原始答复

这段方案是在让系统先从资料库里找出与问题有关的内容，再把找到的片段交给生成模型，帮助它组织回答。RAG 可以理解为“先查资料，再根据资料作答”。

各个词对应流程中的不同工作：

- **Embedding（向量表示）**：把问题转换成一串数值，便于系统按“意思是否相近”来找资料。它是检索用的表示，不是资料本身，也不能证明资料正确。
- **BM25 全文检索**：根据问题中的词语，在资料文字里查找并排序。即使资料没有逐字出现整句问题，也可能因为相关词语而被找到。
- **向量检索**：比较问题和资料片段的向量，寻找表达不同、意思可能相近的内容。
- **RRF**：把全文检索和向量检索各自排出的结果列表合并，主要看每条资料在各列表中的名次，让两种找法的结果能放到一张候选清单里；它不是把两边的原始分数直接相加。
- **Semantic ranker（语义排序器）**：再检查候选片段与问题在语义上是否相关，并重新排序，让更相关的内容靠前。这里的 rerank 就是“重新排序”，不是生成答案或核实事实。
- **生成模型**：把排好序的资料片段和问题一起作为本次回答的上下文，然后组织成文字答复。

组合使用是因为不同检索方式各有长处：BM25 擅长利用具体词语，向量检索能补充表达不同但意思相近的内容；RRF 汇合两边的候选，语义排序器再从中挑出更相关的片段。这样，生成模型就能参考一组更合适的资料来回答。检索到的内容即使排在前面，也不等于它一定充分、可信或正确；最终回答仍取决于所找到的资料和模型如何使用它们。

### 明确读取 Skill：原始答复

这段话描述的是：先用几种方式从资料库里找出可能相关的内容，再把筛选后的片段交给生成模型，让它结合这些资料回答问题。RAG 可以理解为“先查资料，再根据查到的资料组织答案”。

各个词对应的步骤是：

- **Embedding（向量表示）**：把问题转换成一串数字，供系统比较问题和资料在含义上是否接近。它是向量检索的输入，不是资料本身，也不能证明资料正确。
- **BM25 全文检索**：根据问题中的词，在资料文字里查找并排列相关内容。它不只匹配完全相同的句子，也会根据词语在问题和资料中的情况评估相关性。
- **向量检索**：比较问题和资料的向量，寻找含义相近的内容；即使用词不同，也可能找到相关片段。但“意思相近”不等于片段足以支持答案。
- **RRF 合并**：把 BM25 和向量检索各自排出的结果合成一份候选清单。它主要参考每条结果在各自清单里的名次，不是把两种检索的原始分数直接相加。
- **Semantic ranker（语义排序器）**：再看候选片段的文字与问题有多相关，调整它们的顺序。这里的 rerank 就是“重新排序”；它不会替生成模型写答案，也不是事实核验器。
- **生成模型**：把排在前面的资料片段和问题一起作为上下文，据此组织回答。

组合使用，是因为几种方法各有侧重：BM25 擅长利用原文里的词语线索，向量检索能补充用词不同但含义相近的内容；RRF 把两路候选合在一起，语义排序器再细排结果。这样做是为了增加找到相关资料的机会并改善候选顺序，但不能保证检索到的内容正确、完整，也不能保证最终回答一定正确。

### 双方共同的事实资料

该输入举的是一种采用混合检索和可选语义重排的方案，不代表所有 RAG 都必须采用这些组件。

- RAG 在回答时使用外部检索出的资料作为上下文，再由生成模型组织回答。
- embedding 是由模型生成的数值向量表示，可用于表示文本，供向量检索计算相似性。它不是把全文原样复制成数字，也不是自动证明资料正确。
- BM25 属于全文检索的相关性排序方法，使用查询词与文档中的词等信息；不能简单说只会找到完全同一句话。
- 向量检索比较向量表示的相似性，可能找出用词不同但概念相近的内容；相似不等于证据足够或内容可信。
- 在 Azure AI Search 的混合检索例子中，全文与向量查询并行，RRF 按各结果列表中的排名位置融合出一个候选列表，不是直接把不同检索的原始分数相加。
- semantic ranker 在初次 BM25 或 RRF 排序之后，对已有候选文字进行二级相关性排序；这里的 rerank 指重新排序。它不是生成模型的最终回答，也不是事实核验器。
- 检索和排序所得的片段与用户问题组成这次生成可用的上下文。相关、排名靠前、附引用都不能直接保证最终回答正确。

## 接口重试机制

### 共同问题与专业输入

某 AWS 客户端使用 standard retry mode。可重试失败按 exponential backoff 和 jitter 等待，transient error 与 throttling 可能采用不同等待策略；retry quota 用 token bucket 限制持续失败时的重试流量。对支持 client token 的 EC2 操作，还要在同一幂等范围内，保持相同 token 和参数重试，以避免已完成操作被重复执行。

### 未显式加载 Skill：原始答复

它们解决的是重试过程中的不同风险：退避和抖动控制“什么时候再试”，重试额度控制“还能试多少次”，幂等控制“重复提交会不会把业务动作做多次”。

退避让失败后的请求先等一段时间再发。指数退避会随重试次数扩大等待窗口，避免服务刚出问题时客户端立刻连续施压。抖动是在等待窗口内随机选择实际等待时间，避免许多客户端同时失败、又同时重试，形成一波新的请求高峰。暂时性错误和限流错误的等待策略可能不同，因为它们代表的情况不同：前者可能是短暂故障，后者说明服务正在要求客户端减慢速度。

重试额度是给重试流量设一道上限。它用 token bucket 记录可用额度；持续失败会消耗额度，额度耗尽后客户端就停止继续重试并返回错误。这样可以避免一个持续故障被大量重试不断放大。这里的 token 是重试额度的记号。

幂等则解决另一类问题：客户端遇到超时，不一定知道服务端是否已经完成操作。若操作已经完成，客户端再发一次，可能造成重复创建或重复扣款等副作用。对支持 client token 的 EC2 操作，在同一幂等范围内用相同 token 和相同参数重试，可以让服务识别这是同一个请求，避免再执行一次额外动作。它不适用于所有 EC2 API；更换 token 或参数也可能失去这层保护。

所以，等待策略负责减少重试带来的拥挤，重试额度负责限制持续失败时的流量，幂等负责保护业务结果不被重复执行。它们配合使用，但各自处理的问题不同。

### 明确读取 Skill：原始答复

它们处理的是重试中的不同风险：退避和抖动安排请求何时再发，重试额度限制还能发多少次，幂等则避免同一业务操作因重复请求而执行多遍。

- **指数退避**：失败后逐步拉长等待窗口，避免服务正忙时客户端立刻连续重试。**抖动**是在窗口内随机等待，让许多客户端错开重试时间，免得它们又同时涌向服务。具体等待时间不保证每次都比上次长；暂时性错误和限流错误也可能使用不同的等待策略。
- **重试额度**：用一个可消耗、可恢复的预算限制重试流量。持续失败会耗尽预算，客户端便停止重试并返回错误；成功请求可以补回预算。它防的是故障期间重试越积越多、进一步加重服务压力。
- **幂等和 client token**：这是另一层保护。对支持 client token 的 EC2 操作，在同一幂等范围内，用相同 token 和相同参数重试，服务可以识别这是同一个操作，避免再执行一次。例如客户端等到超时，但服务端可能已经完成操作；重试时沿用原 token 和参数，就能防止重复创建等副作用。它不保证请求一定成功，也只适用于支持该机制的操作和相应范围。

所以，退避、抖动和额度管“重试请求怎么进行、何时停止”；幂等管“重复到达的请求会不会重复产生业务动作”。这里的重试额度 token 和 EC2 的 client token 是两种不同东西。

### 双方共同的事实资料

输入组合了客户端重试策略与部分 EC2 API 的幂等能力，二者不属于同一个开关，也不表示所有 API 都支持 client token。

- SDK 是应用用来访问服务的一套开发工具或库。输入限定某 AWS 客户端使用 standard retry mode。
- standard retry mode 对可重试失败采用带 jitter 的指数退避，并受最大尝试次数、重试额度等机制约束；不是任何失败都无条件重试。
- transient error 指可能是暂时性的错误，例如部分网络超时；throttling 表示服务因限流等原因主动拒绝请求。官方当前说明中，两类错误可采用不同退避基数；本题未给数值，不补造配置。
- exponential backoff 按重试次数扩大等待窗口；jitter 在窗口内随机选择等待时间，以分散多个客户端同时重试的流量。不能说每次抽到的实际等待时间都一定比上一次长。
- retry quota 使用 token bucket 管理重试预算。持续失败时预算可耗尽，使客户端不再继续重试并返回错误；请求成功可恢复预算。这里的 token 是额度记号，不是语言模型 token，也不是 EC2 的 client token。
- 对支持 client token 的 EC2 操作，幂等行为由该 API 的约定决定：在同一幂等范围内，用相同 client token 和相同参数重试一个已成功请求，可成功返回而不执行额外动作。区域或可用区范围可影响是否视为同一请求，不能推广成跨区域都不再执行。
- client token 是应用提供的请求标识，不是密码或登录令牌；重试时更换 token 或相关参数，可能失去该重复保护或收到参数不匹配错误。
- 客户端看见超时并不单独证明服务端完全没有执行。重试是否继续，与避免重复业务动作，是不同的问题。
